# ACCEPTANCE.md — 验收标准与证据要求

> 原则：**"编译成功"和"测试通过"都不是验收。** 验收的唯一形式是：人在真实环境里操作，得到可复查的证据。
> 版本：rc3（2026-11-06，按 PR #1 审查意见修订六项；并加入 `published` 默认 `false` 的安全修正）

## 1. 验收角色与签字

| 项 | 谁做 | 产出 |
| --- | --- | --- |
| 功能验收 | QA Agent（A5）独立执行 | `docs/qa/ACCEPTANCE-RUN-<日期>.md` |
| 集成验收 | A1 | PR 中的集成结论 |
| 最终验收 | 用户 | 在 PR/回复中明确确认 |

任何一方缺签，里程碑不算通过。A1 不得替代 A5 出验收结论，A5 不得修改业务代码让自己通过。

## 2. 证据规则

每个验收项必须留下**至少一种**可复查证据：

1. 命令 + 完整输出（粘进验收文档，不截断关键行）。
2. CI 运行链接（`github.com/cvcingcvc-code/141/actions/runs/<id>`）。
3. 截图路径（存 `qa/evidence/<里程碑>/<编号>.png`，截图里要能看到 URL 或时间）。
4. 可被第三人复现的操作步骤序列。

禁止的"证据"：只写"已验证"、只贴 `✓ built in 3.2s`、只给单元测试绿灯、口头确认。

## 7. 隐私验收（P0-1，三层检查，缺一层不算过）

| 层 | 检查 | 通过标准 |
| --- | --- | --- |
| L1 工作树 | `git grep -nE "邮箱/手机号/身份证/sk-/ghp_/AKIA/PRIVATE KEY"`，覆盖**全部**已跟踪文件（含 draft、`published:false`） | 0 命中，或命中项为明确的假值（如文档里的示例 `someone@example.com` 需白名单化并说明） |
| L2 git 历史 | `qa/scripts/privacy-scan.mjs` 遍历提交（至少最近 50 个 + 全部涉及 `content/` 的提交） | 0 命中真实 PII/凭据 |
| L3 构建产物 | 扫描 `dist/**` | 0 命中；且 0 条 L3 内容、0 条 draft |

另外必须显式确认：
- [ ] 仓库内**没有任何** L3（私密原文/他人隐私/健康家庭细节）内容
- [ ] 所有 L3 内容只以 `vault_ref` 指针存在，且 `F:\141-vault\` 不在 git 中（`git check-ignore` 或目录不在仓库路径内）
- [ ] 若曾发生泄漏，`docs/incidents/` 有对应记录且凭据已轮换

## 9. 验收不通过的典型情形（一律打回）

1. 用 `npm run build` 成功代替页面可用。
2. 页面能打开但数据是硬编码的假数据。
3. 搜索能出结果但点进去 404。
4. 样本内容被当成真实内容（未标 `sample`）。
5. 修复缺陷时顺手重构无关模块（扩大范围）。
6. 验收文档里出现"应该""大概""理论上"。
7. 只跑了红灯用例，没跑正向用例（§5）。
8. 隐私只扫了 `dist/`，没扫工作树与历史。

## 10. 回滚标准

出现以下任一情况，立即回滚该 PR 并记录：
- 公开站点出现 draft / L3 内容；
- `main` 构建失败；
- 内容被覆盖或删除（非本人 PR 造成）；
- 保护规则导致正常合并无法完成（视为配置缺陷，先回退保护再修）。

## 11. 分支保护验收（P0-2 专项）

| 检查 | 通过标准 |
| --- | --- |
| 无外部审批人要求 | 保护设置里 `required_approving_review_count = 0` |
| 仍需 PR | 直推 main 被拒 |
| 禁 force push | `git push --force` 被拒（贴报错） |
| 检查名真实存在 | required checks 的名字取自 `gh api .../check-runs` 实际输出，不是猜测 |
| 可自行合并 | A1 完成一次完整 PR 合并，附 run 链接 |
| 不自锁 | 若 CI 因基础设施故障挂掉，有记录的临时降级步骤（关保护 → 修 → 重新开启），且必须写进 PR |

不得为了"看起来严格"而开启任何无人能满足的条件。
