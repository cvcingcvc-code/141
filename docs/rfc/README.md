# RFC 流程 — 契约变更申请

契约（`docs/CONTRACTS.md`）一旦冻结，任何修改都必须先有 RFC。这是防止多 Agent 并行时契约漂移的唯一机制。

## 什么时候必须提 RFC

| 变更 | 需要 RFC |
| --- | --- |
| 新增/修改/删除 frontmatter 字段或枚举值 | ✅ |
| 修改 id 格式、文件命名、目录结构 | ✅ |
| 新增/修改路由 | ✅ |
| 修改 `content.json` 形状（v0.1 仅此一个产物） | ✅ |
| 新增/修改 `package.json` 脚本语义或依赖 | ✅ |
| 新增页面但复用现有契约与数据 | ❌（按 TASKS 正常走） |
| 修 bug 不改变对外形状 | ❌ |
| 调整样式、文案、布局 | ❌ |

## 流程

1. 复制 `RFC-TEMPLATE.md` 为 `RFC-<三位序号>-<kebab-slug>.md`。
2. 填完「动机 / 影响面 / 迁移 / 回滚」，**状态填 `proposed`**。
3. 开 PR，标题 `docs(rfc): RFC-00X <标题>`，打 `contract-change` 标签。
4. 主 Agent 审：批准 → 状态改 `accepted`；驳回 → `rejected` 并写明理由（不要删文件，保留决策记录）。
5. 实施 PR 中必须同时改：`CONTRACTS.md`（升版本 + 冻结记录）、`schema.ts`、`validate-content.mjs`、受影响页面与 `content/**`。
6. 三方不一致 = 契约撕裂，一律打回。

## 版本号规则

- `1.0.x`：澄清、修错别字、补示例，不改变任何形状。
- `1.1.0`：新增可选字段、新增路由（向后兼容）。
- `2.0.0`：删除字段、改语义、改 id 格式（破坏兼容，必须附迁移脚本）。

## 禁止

- 先改代码再补 RFC（顺序颠倒即为违规）。
- 一个 RFC 夹带多个无关变更。
- 在 RFC 未获批时把代码合进 `main`。
